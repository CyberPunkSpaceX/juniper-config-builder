How to use it

A beginner's guide to Multi-Vendor Switch Config Builder {{ version }}. You fill in forms, and the switch configuration appears live on the right, ready to copy or download and paste onto the switch.

1. Getting started

  1. Pick Production or Lab right after you sign in. Production is the real network; Lab is for testing, with the EVE-NG lab tools. Each has its own saved projects, maps and backups. Switch any time with the Production | Lab button in the top bar.
  2. Pick the client you're working for (if you're in more than one). Change it later with the Client list in the top bar.
  3. Pick a vendor (Vendors in the top bar takes you back). The builder only offers what that vendor's switches can do, so options that would give config the switch can't load are hidden.
  4. Pick Basic or Advanced (top left of the builder). Basic shows what a normal access switch needs. Advanced adds routing protocols and the less common fields; those sit in a purple dashed Advanced options box so you can tell them apart. Switching back to Basic keeps what you set.
  5. Start from something: pick your model on the Switch tab, or load an example from the list at the top. Each vendor has at least one example.
  6. Work through the tabs from top to bottom. The config on the right updates as you type.
  7. Copy or Download the config and load it on the switch (see Loading the config).

2. The tabs, step by step

Switch

Pick the model. Add a row per switch to build a stack (Juniper Virtual Chassis, Cisco StackWise, Ruckus/Brocade stacking). The member number becomes the first number in the port names (for example Gi2/0/1 on Cisco, 2/1/1 on Ruckus). Use Custom for a model that isn't listed, and add its ports under Custom ports.

System

Host name, domain, time zone, DNS and NTP servers, the login banner and the management port. The management VRF keeps management traffic (SSH, SNMP, logs) apart from user traffic.

Users

The root (or enable / admin) password and local accounts. super-user can change everything, operator can look and clear counters, read-only can only look. Add SSH public keys to log in without a password. SSH is always on; Telnet is always off.

SNMP & logs

SNMP lets monitoring tools read the switch. Use a hard-to-guess community name and list the monitoring servers under clients, or use SNMPv3 users. Syslog servers receive the switch's log messages.

VLANs

Each VLAN needs a name and an ID (1-4094). Give a VLAN an address (the "IRB", SVI or VE interface) if the switch should route for it. Tick DHCP relay when the DHCP server is in another VLAN, and Voice VLAN to hand that VLAN to every phone port.

Ports

A port group gives the same settings to many ports. Modes:

  • access: one untagged VLAN, for PCs, printers and phones (plus an optional voice VLAN).
  • trunk: several tagged VLANs, for uplinks, access points and other switches. The native VLAN is the one sent untagged.
  • routed: a layer 3 port with its own IP address (one port per group).
  • disabled: switched off.

Tick Edge on ports where only end devices plug in: they come up fast and are protected from loops. Connected devices (phones, access points, cameras) only colours the port map.

LAGs

A LAG bundles several links into one for more speed and redundancy. Use LACP active on at least one end. Both ends must have the same VLANs. The other switch must have a LAG too.

Routing

Static routes (the default route is 0.0.0.0/0), the DHCP servers for DHCP relay, and in Advanced mode the loopback, router ID, OSPF and BGP.

Services

LLDP (lets switches and phones discover each other), spanning tree, storm control, PoE, DHCP snooping, 802.1X with RADIUS servers, and Disable unused ports.

3. The port map

  • Click free ports to pick them (Shift-click picks a whole range), then New port group or New LAG, or add them to an existing group.
  • Click a port that is already in a group to edit that group: its ports light up, click ports to add or remove them, then Save. A port added to one group is taken out of any other.
  • The colour shows what each port does. Dashed ports are not provisioned (for example a missing module); crossed-out ports are disabled. A dot means PoE.

4. Errors and warnings

  • Red errors are things the switch would refuse. The field is outlined in red and its tab turns red with a count. Click an error to jump to the field.
  • Orange warnings are things to double-check, or settings this vendor's builder doesn't write. The config still works.

5. Loading the config on a switch

Always keep a way back: a console cable, a backup of the current config, and a timer that undoes the change if you lose the connection. The steps for each vendor are below the config in the builder, and here:

Pushing from the builder (with automatic rollback)

Admins of a client can push an approved Production project straight to the switch: Projects tab (Production space) → Push to a switch.

  1. Preview changes: the running config is kept as a backup first, then the switch shows what would change (show | compare) and runs commit check. Nothing changes yet.
  2. Push with auto-rollback: the switch commits with its own safe-revert timer (1 to 60 minutes, 10 by default): Juniper commit confirmed, Arista commit timer in a config session, Cisco configure terminal revert timer (the config archive is turned on if needed), Aruba CX checkpoint auto, Nexus a checkpoint plus a one-time scheduler job that rolls back to it, MikroTik Safe Mode in a session the server keeps open. Confirming also saves the config on vendors that have a startup config.
  3. The page signs in again to check the switch is still reachable. Click Keep the change before the timer ends, or Roll back now. If you do nothing, or the change cuts the switch off, it puts the old config back by itself.

Only projects approved and promoted from the Lab can be pushed, the switch must be in the client's SSH networks and fetched over SSH once (so its key is known), and a switch whose name differs from the project's needs an extra tick. Juniper and Arista show the switch's own diff; for Cisco, Nexus and Aruba CX the builder works out what is new, and MikroTik shows the script. Dell OS10, Extreme, Ruckus and ProCurve have no automatic rollback and can't be pushed yet; UniFi is set up in the UniFi app. EXB_PUSH_DISABLE=true turns pushing off.

Juniper (Junos)

  1. cli, then configure.
  2. Paste the set commands. (For the curly-brace format: load merge terminal, paste, Ctrl+D.)
  3. show | compare to see the change, commit check to test it.
  4. commit confirmed 5. If you're still connected, commit again to keep it; otherwise the switch rolls back by itself after 5 minutes.

"Start with delete interfaces / delete vlans" (on by default) clears the factory port settings first. Turn it off when you only want to add to an existing config.

Arista (EOS)

  1. configure session new, paste, show session-config diffs.
  2. commit timer 00:05:00, then commit again once you're still connected.

Cisco (IOS-XE)

  1. Back up first: copy running-config flash:before.cfg.
  2. On a remote switch: reload in 10 (undo after 10 minutes if you lose access).
  3. configure terminal, paste, end, check with show running-config.
  4. reload cancel, then write memory.

Cisco Nexus (NX-OS)

  1. Save a restore point: checkpoint before-change.
  2. configure terminal, paste, end, check with show running-config.
  3. If something is wrong: rollback running-config checkpoint before-change.
  4. copy running-config startup-config to keep it.

Fortinet FortiSwitch (standalone)

  1. Back up first: execute backup config tftp before.conf <server>.
  2. Paste the commands at the prompt. Each config ... end block applies when it reaches end, and FortiSwitchOS saves changes as it goes.
  3. Check with show. To undo: execute restore config tftp before.conf <server> (the switch reboots).

Ubiquiti UniFi

  1. UniFi switches take no commands: the builder makes a settings sheet for the UniFi Network app.
  2. Make a backup first (Settings > System > Backups) and adopt the switch.
  3. Work through the sheet from top to bottom: networks, global switch settings, port profiles, the switch itself, aggregates and then the ports. Type passwords and secrets in the app; the sheet never prints them.
  4. Click Apply Changes. The switch provisions itself, which takes about a minute.

MikroTik (RouterOS v7)

  1. Back up first: /export file=before.
  2. Press Ctrl+X to turn on Safe Mode. If you lose the connection, RouterOS undoes everything you changed.
  3. Paste the script, or upload it as change.rsc and run /import file-name=change.rsc. VLAN filtering is switched on in the very last line, so that is the moment a wrong VLAN table would cut you off.
  4. Check with /interface bridge vlan print. When everything works, press Ctrl+X again to leave Safe Mode and keep the changes. RouterOS saves changes as it goes.

Extreme Networks (EXOS / Switch Engine)

  1. Back up first: save configuration before-change, and answer No when it asks to make it the default.
  2. Paste the commands, or upload them as change.xsf and run load script change.xsf.
  3. Check with show configuration, then save configuration.
  4. To undo: use configuration before-change, then reboot.

Dell (OS10)

  1. Back up first: copy running-configuration config://before.xml.
  2. configure terminal, paste, end, check with show running-configuration.
  3. To undo: copy config://before.xml running-configuration.
  4. write memory to keep it.

Brocade / Ruckus (FastIron)

  1. Back up first: copy running-config tftp <server> before.cfg.
  2. On a remote switch: reload after 00:00:10 (10 minutes).
  3. configure terminal, paste, end, check with show running-config.
  4. reload cancel, then write memory.

HPE Aruba / ProCurve (AOS-S)

  1. Back up first: copy running-config tftp <server> before.cfg.
  2. On a remote switch: reload after 10 (reboots to the saved config after 10 minutes).
  3. configure terminal, paste, check with show running-config.
  4. no reload, then write memory.

HPE Aruba CX (AOS-CX)

  1. Save a restore point: copy running-config checkpoint before-change.
  2. On a remote switch: checkpoint auto 10 (rolls back after 10 minutes unless you confirm).
  3. configure terminal, paste, end, check with show running-config.
  4. checkpoint auto confirm, then write memory. To undo later: checkpoint rollback before-change.

6. Notes per vendor

Juniper (Junos ELS): EX2300, EX3400, EX4100, EX4300, EX4400

  • Ports: ge-0/0/0 (1G), mge- (multi-gig), xe- (10G); the first number is the Virtual Chassis member. LAGs are ae0, ae1 and so on.
  • Everything in the builder is available, including policies, EVPN-VXLAN, QoS and all the Tools.

Arista (EOS): 720XP, 722XPM, 7010, 7050X3, vEOS and cEOS lab

  • Ports: Ethernet1 (short: Et1-24); QSFP lanes are Ethernet49/1. LAGs are Port-Channel1.
  • Not written yet: EVPN-VXLAN, policies, QoS and the Tools.

Cisco (IOS-XE and IOS): Catalyst 9200, 9300, 9500, older 2960-X, 3650, 3850, and Cat9kv lab

  • Ports: GigabitEthernet1/0/1 (short: Gi1/0/1-24, Te1/1/1). The first number is the stack member (1-8); slot 1 is the uplink module. LAGs are Port-channel1 (Po1).
  • The root password becomes the enable secret. Cisco needs a domain name to make the SSH key.
  • The 9200 can't translate VLANs; you get a warning.
  • Older switches: the 3650 and 3850 run IOS-XE 16 and get the same config as the 9300. The 2960-X runs classic IOS 15.2, so it gets type 5 secrets, ip domain-name, its management port FastEthernet0 with ip default-gateway (no management VRF), and no VLAN mapping. It only does static routes, after sdm prefer lanbase-routing and a reload; OSPF and BGP give an error.

Cisco Nexus (NX-OS): Nexus 9200, 9300, older 3000, and the Nexus 9000v lab

  • Ports: Ethernet1/1 (short: Eth1/1-48); breakout lanes are Ethernet1/49/1. LAGs are port-channel1 (Po1). Nexus switches don't stack: a vPC pair is two projects.
  • The config starts with the feature lines it needs (lacp, interface-vlan, ospf, bgp, dhcp and so on).
  • The management port mgmt0 is always in the management VRF, and its gateway goes there. With "Management VRF" ticked (the default), NTP, DNS, logging, SNMP and RADIUS also go out through mgmt0.
  • The root password sets the built-in admin user. Passwords become SHA-256 hashes (password 5).
  • NX-OS wants a fixed offset for the time zone, so summer time needs a clock summer-time line added by hand.
  • No PoE and no voice VLAN on Nexus. The Nexus 3000 can't translate VLANs.
  • Not written yet: EVPN-VXLAN, vPC, policies, QoS and the Tools.

Fortinet FortiSwitch (FortiSwitchOS, standalone): FS-108F, 124F, 148F, 248E, 424E, 448E, 1048E

  • This is for a standalone FortiSwitch. One managed by a FortiGate (FortiLink) is set up on the FortiGate.
  • Ports: port1 (short: 1-24). LAGs are trunks (lag1). FortiSwitches don't stack.
  • A port's untagged VLAN is its native-vlan and its tagged VLANs are allowed-vlans. A VLAN address is a config system interface entry on internal; there are no routed ports.
  • The 100F series has no out-of-band port; manage it through a VLAN address.
  • OSPF and BGP need the Advanced Features license (400 series and up).
  • Passwords go in as plain text and the switch encrypts them. The time zone is picked from a numbered list on the switch, so it is not written.
  • Not written yet: the time zone, login banner, SNMPv3, storm control, PoE power limits, the LLDP-MED voice profile, VLAN translation, EVPN, policies, QoS and the Tools.

Ubiquiti UniFi: USW Lite, Standard, Pro, Pro Max and Aggregation

  • The output is a settings sheet for the UniFi Network app (menu names from version 9), not a config to paste.
  • Ports are numbered 1-24. Each port group becomes an Ethernet port profile; groups with the same settings share one profile. Aggregates (LAGs) must be neighbouring ports and always run LACP.
  • A VLAN address needs a Layer 3 model (Pro, Pro Max, Pro Aggregation): the switch then routes that network. On the others, leave VLAN addresses empty and let the gateway route.
  • The devices have one SSH login, made from the first super-user. People who manage the network get UniFi OS accounts.
  • Not available on UniFi: stacking, routed ports, OSPF, BGP, MAC limits, PoE priority, ARP inspection, VLAN translation and EVPN.

MikroTik (RouterOS v7): CRS326, CRS328, CRS354, CRS310, CRS317 and CHR

  • Ports keep their RouterOS names: ether1, sfp-sfpplus1. LAGs are bonds (bond1). MikroTik switches don't stack.
  • All ports join one bridge, bridge1, with hardware VLAN filtering. A port's untagged VLAN is its pvid; the VLAN table is in /interface bridge vlan. A VLAN address is a VLAN interface (vlan10) on the bridge, and the bridge is tagged in that VLAN for you.
  • There is no separate management port. Manage the switch through a VLAN address, or name a port as the management port: it leaves the bridge and gets the address.
  • Load it in Safe Mode: VLAN filtering is switched on last, and a mistake there can lock you out.
  • Passwords go in as plain text and RouterOS stores them hashed. SSH keys need RouterOS 7.12 or later.
  • Not written yet: routed ports, port speed, MAC limits, ARP inspection, SNMPv3, PoE power limits, VLAN translation, EVPN, policies, QoS and the Tools.

Extreme Networks (EXOS / Switch Engine): X440-G2, X450-G2, X460-G2, 5320, 5420 and the EXOS VM

  • Ports: 1 to 52; in a SummitStack slot:port (2:1). The output is a list of one-line commands, like a script.
  • VLANs have names and take their ports (configure vlan USERS add ports 1-40 untagged). Every port starts in the Default VLAN, so the script empties it first. VLAN 1 is Default, so use IDs 2-4094.
  • A LAG is a sharing group named after its first port (the master port): enable sharing 49 grouping 49-50 ... lacp. The master port stands for the LAG in VLANs.
  • There are no routed ports: put the address on a VLAN. OSPF needs the Advanced Edge license and BGP the Core license.
  • Users are created with plain-text passwords, which EXOS encrypts. The built-in admin password is set at the CLI.
  • Not written yet: 802.1X / MAB (netlogin), SNMPv3, the login banner, storm control, OSPF authentication, VLAN translation, EVPN, policies, QoS and the Tools.

Dell (SmartFabric OS10): N3248TE, N3248P, N3248PXE, N2248PX, S5248F, S5232F and the OS10 virtual lab

  • Ports: ethernet1/1/1 (short: eth1/1/1-24). Port groups become interface range blocks. LAGs are port-channel1 (Po1). OS10 doesn't stack: a VLT pair is two projects.
  • A VLAN is an interface vlan10; its name goes in the description and its address on the same interface. On a trunk, the native (untagged) VLAN is the port's switchport access vlan.
  • The management port mgmt1/1/1 gets its gateway with management route.
  • The root password sets the built-in admin user. Passwords become SHA-512 hashes and need at least 9 characters. SSH keys are loaded from a file on the switch, so add them by hand.
  • Not written yet: PoE settings, port security, voice VLAN, MAB, storm control, OSPF authentication, VLAN translation, EVPN, policies, QoS and the Tools.

Brocade / Ruckus (FastIron): ICX 7000 and 6000, FCX, FGS, FLS

  • Ports: 1/1/1 (unit/module/port); ethe 1/1/1 also works. FGS and FLS don't stack and number their ports 0/1/1. LAGs are lag1.
  • FastIron lists ports inside each VLAN (tagged or untagged) instead of listing VLANs on each port; the builder works this out for you. VLAN addresses become ve interfaces.
  • Older switches (ICX 6000, FCX, FGS, FLS) get the older commands they need, such as dual-mode and sntp.
  • Not written: storm control (FastIron uses a rate, not a percentage) and VLAN translation.

HPE Aruba CX (AOS-CX): CX 6000, 6100, 6200, 6300, 8320, 8325, 8360 and the CX simulator

  • Ports: 1/1/1 (member/slot/port); ranges like 1/1/1-1/1/24 or 1/1/1-24. The 6200 and 6300 stack with VSF (members 1-10). LAGs are lag1; VLAN addresses are interface vlan 20.
  • The root password sets the built-in admin user. AOS-CX encrypts passwords with its own key, so the config carries them as plain text and the switch encrypts them when you load it. They stay readable in the saved project, so keep it private.
  • The management port (mgmt) is always in the mgmt VRF. The 6000 and 6100 have no management port; manage them through a VLAN address.
  • Phone ports become "native VLAN + voice VLAN" trunks, which is how AOS-CX hands a voice VLAN to phones.
  • Not written yet: storm control, VLAN translation, EVPN, policies, QoS and the Tools.

HPE Aruba / ProCurve (AOS-S): 2530, 2540, 2920, 2930F, 2930M, 3810M, 5400R and older ProCurve 2610, 2810, 2910al

  • Ports: 1 to 48, module ports A1; the 2930M and 3810M use 1/1 (member/port) and stack (members 1-10). LAGs are trunks: Trk1.
  • Like FastIron, AOS-S lists the ports inside each VLAN (untagged 1-40, tagged Trk1), and the VLAN holds its IP address. There are no routed ports: OSPF runs on VLANs.
  • A switch with one VLAN address and only a default route stays layer 2 and gets ip default-gateway; more VLAN addresses, other routes or OSPF turn on ip routing.
  • AOS-S has one manager and one operator account. Passwords go in as plain text and the switch hashes them.
  • The output has no comment lines, because the AOS-S command line doesn't accept them.
  • Not written: BGP, SNMPv3, storm control, VLAN translation, policies, QoS and the Tools.

7. VLAN translation

On a trunk port (Advanced mode) write pairs such as 120>20, 130>30: frames that arrive tagged 120 join VLAN 20 on this switch and leave tagged 120 again. Useful when a carrier or another site uses different VLAN numbers. The wire VLAN (120) must not also be a VLAN on this switch.

  • Juniper: vlan-rewrite on EX4100, EX4300 and EX4400 (not EX2300 or EX3400).
  • Arista: switchport vlan translation.
  • Cisco: switchport vlan mapping on the 9300, 9500, 3650 and 3850 (not the 9200 or 2960-X).
  • Cisco Nexus: switchport vlan mapping on the Nexus 9000 (not the 3000).
  • Dell OS10: not available.
  • Extreme EXOS: not written.
  • FortiSwitch: not written.
  • MikroTik: not written.
  • UniFi: not available.
  • Brocade / Ruckus: not available.
  • HPE Aruba CX: not written yet.
  • HPE Aruba / ProCurve (AOS-S): not available.

8. Passwords and secrets

  • Passwords are turned into hashes as soon as the config is made (SHA-512 on Juniper and Arista, type 8 on Cisco (type 5 on the 2960-X), SHA-256 on Nexus, SHA-512 on Dell, MD5-crypt on Ruckus), so plain text is never saved in a project. The exceptions are Aruba CX, AOS-S, Extreme EXOS, FortiSwitch and MikroTik, which only take plain-text passwords in a pasted config. The UniFi settings sheet never prints passwords: you type them in the app.
  • A hash only works for the vendor it was made for. Copy a project to another vendor and you'll be asked to type the passwords again.
  • SNMP communities, RADIUS secrets and BGP/OSPF keys are in the config as you typed them. Keep downloaded configs and projects somewhere safe.

9. Projects and clients

  • Projects (under Tools) saves your work on the server, in the client and space (Production or Lab) picked at the top of the page. You can also download a project as a JSON file and open it later.
  • Production and Lab are kept apart: a project, map or config backup saved in Lab is not shown in Production, and the other way round.
  • From Lab to Production, with approval: save the tested project in Lab, then in Projects click Ask for approval (editors and admins). The project is frozen as it is then, and it must have no errors. A client admin or a Super Admin opens it, then clicks Approve or Reject (with a reason). Admins and Super Admins may approve their own requests; a Configurator's request needs one of them. Then an admin clicks Promote to Production: the approved version is copied into Production under the same name. If the Lab project was changed after approval, it has to be approved again. A Production project with the same name is replaced, and Undo puts it back. Every step is listed with who did it and when.
  • Your unsaved work is kept in the browser per client, space and vendor, so it never follows you into another client, and Arista work doesn't overwrite Juniper work.
  • A client is a customer or network. People only see the clients they're added to, as Read-only (look, with passwords, keys and SNMP communities hidden), Configurator (build, save and delete) or Admin (also manage people, SSH and EVE-NG settings, approve Lab work). A Super Admin manages every client and the users. A Super Admin can give someone a level in all clients, which includes clients added later, or in chosen clients only.
  • A client admin can Download a backup of a client (projects, maps, config backups) on the client's page.
  • Nightly backups: on the client's page a client admin lists the switches (address, vendor, port), the time, and who hears about changes (email, Teams, Slack or Discord). Each night every switch is read with the client's SSH key; a changed config is kept as a new version and the alert shows the changed lines. Changes on any backup (Backups & compare tab) shows what changed since the version before.
  • Switch logs: point the switches' syslog at this server (port 514). On the client's page a client admin turns logs on and lists the networks the switches send from; each client sees only its own logs on the Logs page (search, filters, live view, CSV), and can get an alert for serious messages.

10. Tools (Juniper for now)

  • Import…: paste an existing config (or drop a file) and Check config. It's read into the tabs, gets a score out of 100, and a list of recommendations. Load with recommended fixes applies the safe ones. The Excel template is here too.
  • Network map: drop several switch configs (or a .zip) to draw the switches and the links between them, and check that both ends of each link agree. Client admins can fetch configs straight from the switches over SSH (read-only commands only, inside the client's allowed networks).
  • EVE-NG lab (Lab space only, every vendor that has a lab image): see Testing in EVE-NG.
  • Backups & compare: keeps every fetched config, and compares any two configs (live, backup, builder, lab or pasted), with the commands that make one like the other.
  • EVPN-VXLAN fabric wizard (Advanced): pick a fabric type and the number of switches; it works out every address and writes one config per switch.

11. Testing in EVE-NG

With an EVE-NG server you can try a config on a virtual switch before it goes near a real one. Labs live in the Lab space, so test configs never mix with production ones.

Set it up once

  1. Install the images on the EVE-NG server the usual EVE-NG way (copy the image to /opt/unetlab/addons/qemu/<type>-<version>/ and run /opt/unetlab/wrappers/unl_wrapper -a fixpermissions). The images come from each vendor's download site with your account.
  2. A client admin opens Clients → (client) → EVE-NG lab server, enters the EVE-NG address, an EVE-NG account made for the builder and the lab folder, then clicks Test the connection. It lists the lab images it found.

Build a lab

  1. Click Lab at the top, open the client and the vendor, and build the switch as usual (no errors left).
  2. Open the EVE-NG lab tab (under Tools), pick the image, name the lab and click Build this switch in EVE-NG.
  3. The builder moves the ports the project uses onto the lab switch's ports, in order (every port group and LAG gets at least one; the mapping is listed under the lab). It leaves out other stack members, the management address and the banner, and adds a lab login exb-lab with a random password.
  4. With Start the lab and load the config ticked, the lab starts, the builder answers the switch's first-boot questions on its console, types the config in line by line and saves it. Lines the switch refuses are listed in the progress. Booting takes from 1 minute (CHR) to 15 minutes (Cat9kv); you can leave the page.
  5. In EVE-NG, connect the node's ports to other nodes or networks and test.
  6. Pull configs reads the config back over the console, with the project's port names again and without the lab login, so you can compare it or download it.

For Juniper there is also Build lab from the map: every switch on the network map becomes a vJunos node, cabled like the map.

12. Converting a config to another vendor

Open Converter (on the first screen after sign-in, or in the top bar). Paste the old switch's running config, or open it from a file.

  1. From: leave it on Detect it for me, or pick the vendor. Configs from Cisco Catalyst (IOS and IOS-XE), Cisco Nexus (NX-OS), Arista EOS, Dell OS10 and Juniper EX can be read today; the other vendors are coming.
  2. To: the vendor of the new switch. New switch model: pick it, or let the converter pick the smallest model with enough ports (and PoE, stacking and a management port when the old one had them).
  3. Press Convert. Ports move by position: the old switch's front port 1 becomes the new switch's front port 1, and uplinks stay uplinks. The port map at the bottom of the report shows every move.
  4. Read the report. Fix before loading lists what the new vendor's builder refuses (most often passwords: hashed passwords can't move between vendors, so type new ones). Not carried over lists what was left out, and Lines not read lists every line of the old config the converter did not understand, such as access lists and QoS policies. Nothing is dropped without being listed.
  5. Pick the client and press Save to Lab, then Open it in the Lab. Fix what the report asked for, test it (an EVE-NG lab if the vendor has one), and use Ask for approval on the Projects tab to promote it to Production.

13. Words you'll see

  • VLAN: a separate network on the same switch. Tagged frames carry the VLAN number; untagged don't.
  • Trunk: a port that carries several VLANs, tagged. Native VLAN: the one sent untagged on a trunk.
  • LAG / LACP: several cables working as one link; LACP checks both ends agree.
  • IRB / SVI / VE: the switch's own address in a VLAN, so it can route for it (the names differ per vendor).
  • Spanning tree (RSTP): stops cabling loops from taking the network down.
  • PoE: power over the network cable for phones, access points and cameras.
  • 802.1X / MAB: devices must log in (or be known by MAC address) through a RADIUS server before the port lets them on.
  • DHCP snooping: only trusted ports (uplinks) may answer DHCP, which stops rogue DHCP servers.

14. The Toolkit (many switches at once)

Open Toolkit in the top bar. Its tools use the client and the Production or Lab space picked at the top.

Bulk build

  1. Build one switch the way you want every switch to look and save it as a project. Where a value changes per switch, you can write a placeholder such as {{ '{{' }}site{{ '}}' }}, for example an SVI address of 10.{{ '{{' }}site{{ '}}' }}.20.1/24.
  2. On Bulk build, pick that project as the template (or open a project .json file).
  3. Paste a spreadsheet with one line per switch, or open a .csv file. Download a starting spreadsheet gives you the right column names. Usual columns: hostname (required), mgmt_address, mgmt_gateway, model, serial, location, contact, domain. A column named like a placeholder fills it. A column such as vlans.MGMT.irb or system.banner sets that field directly.
  4. Build all. Each line shows whether it built, with its problems: a hostname or management IP used twice, an empty placeholder, or the builder's own errors.
  5. Download zip gives every config, every project and a summary sheet. Save all as projects saves each switch as its own project (editor role needed).

Pre-push checks

Each builder checks its own switch. Pre-push checks looks at several saved projects together. Tick the projects and Run checks. It reports:

  • the same host name or IP address (management, loopback, VLAN interface, routed port) on two switches, one subnet on different VLANs, and VLAN IDs or names that do not match between switches;
  • links whose ends disagree: access against trunk, a LAG on one end only, both ends LACP passive, a different native VLAN, VLANs allowed on one end only or missing on the far switch, routed ends in different subnets, and MTU differences;
  • VLANs used on a switch's ports that no uplink carries;
  • spanning tree: different protocols, no bridge priority anywhere, or a tie for the root.

Links are found from port-group and LAG descriptions that name the other switch (To core-sw1). Add any others with Add a link by hand. Ready to push means no errors were found; still read the warnings.

NetBox sync

A client admin opens NetBox sync and enters the NetBox address and an API token (stored encrypted). The address must be inside the networks this server may reach. Then pick a NetBox site:

  • Pull from NetBox turns the site's switches into projects: host name, model, serial, management IP (the device's primary IPv4), the site as SNMP location, the site's VLANs and the VLAN interface addresses NetBox has. Pick saved projects as templates (one per brand) so ports and services follow your standard. Devices of other makers (PDUs, firewalls) are listed but skipped.
  • Push to NetBox (client admin) shows what would change first: missing VLANs, missing IP addresses (assigned to the device's interface when NetBox has it), serial numbers, and devices NetBox doesn't have yet (pick a role; they are added as "planned"). Tick what you want and Make these changes in NetBox. Nothing in NetBox is deleted.

Auto network map

Draws switches and cables from LLDP and CDP neighbours, for every brand. Either paste each switch's neighbour output (show lldp neighbors detail, show cdp neighbors detail, Juniper show lldp neighbors, Aruba CX show lldp neighbor-info detail, ProCurve show lldp info remote-device detail, Extreme show lldp neighbors detailed, FortiSwitch get switch lldp neighbors-detail, MikroTik /ip neighbor print detail), or, as a client admin, Fetch over SSH: give one or two switches to start from and it logs in, reads the neighbours with read-only commands, and follows their management addresses inside the client's allowed networks. Green lines are seen from both ends; dashed lines and boxes are only seen from one side. Download the picture (SVG) or the list of links (CSV).

Compliance

Scores each switch out of 100 against the client's standard: NTP, remote syslog, DNS, SNMPv3 only, no public/private community, login banner, telnet and plain HTTP off, SSH root login denied, time zone, BPDU guard on edge ports, unused ports disabled and named admin accounts. A client admin switches rules on or off, sets their weight and values (for example the NTP servers every switch must use) under The standard. Check saved projects, the latest backup of each switch, or a pasted running config. Running configs are read with the Converter's readers where the brand has one, plus text checks; a rule that cannot be told from a config shows as "can't tell" and doesn't count. Download the report gives a CSV with every rule per switch.

Calculators

  • Subnet: an address with prefix (or mask) gives the network, mask, wildcard, first and last host, broadcast and the number of hosts. Split a network by number of subnets, hosts per subnet or new prefix.
  • VLAN plan: give an address block and each VLAN's name, ID and number of devices (plus room to grow). Each VLAN gets the smallest subnet that fits, biggest first, with the gateway on the first or last address. Add to project puts the VLANs (and the gateway as VLAN interface address) into a saved project; VLANs it already has are left alone.
  • PoE budget: the switch's PoE budget and the devices on it. Most switches reserve power by PoE class, so the reserved total can run out before the devices actually draw it all.

Firmware tracker

Lists the software version of every switch, read from its latest config backup (SSH fetch, nightly backups or uploads), and checks it against the client's policy. A client admin adds one line per brand, or per model family when they differ, with a minimum version, a recommended version and known-bad versions (22.2R1, < 21.4R3, 17.9.1 - 17.9.3 or 16.12*, each with a note such as the advisory number). Each switch shows as Known bad, Below minimum, Update, OK or Unknown. Nothing is looked up on the internet, so keep the policy current from the vendors' security advisories. You can also paste show version output for switches that have no backup.

Audit log & API

The audit log keeps every change made in the app: who, when, from which address, in which client and space, what was asked and whether it worked. Sign-ins and failed sign-ins, SSH fetches, nightly backups and settings changes are there too. Request bodies are never stored, so passwords and secrets stay out of it. A server admin sees everything, a client admin sees the rows of their clients. Filter by user, client, kind, date or text, and download the result as CSV. Rows are kept 365 days (EXB_AUDIT_DAYS changes that).

The same page lists the scripting API under /api/v1/: your clients, projects (read, get the config, create or replace one), config backups and the audit log. Sign in with HTTP Basic auth using your user name and the API token from your account page. Changes made over the API land in the audit log as well.
